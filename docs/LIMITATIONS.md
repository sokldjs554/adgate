# 한계

이 저장소가 *보여 주지 못하는 것*을 먼저 적는다. 여기 적힌 것을 읽지 않고 수치만 가져가면 오해한다.

## 1. 데이터와 정책

- **모든 광고는 합성이고, 정책은 가상이다.** 실제 업체·상품·법령과 무관하다. 어떤 회사의 실제 심사 기준이나 법률 자문이 아니다.
- **같은 사람이 정책, 탐지기, `dev`, `test` 를 모두 썼다.** 같은 가정을 공유하므로 `test` 는 순수한 일반화의 증거가 아니다. `test` 는 탐지기 코드보다 먼저 써서 동결했고, 그 *첫 측정*만 holdout 이다(첫 측정 뒤 한 건을 고쳤다 — [FAILURES.md](FAILURES.md) F-2).
  게다가 `adgate gate`(CI 가 push 마다 돌린다)와 pytest 가 `test` 를 회귀 감시용으로 매번 읽는다. 그 읽기는 기록되지 않는다([DECISIONS.md D-5](DECISIONS.md)). **`test` 의 현재 수치는 증거로 쓰지 않는다.**
- **독립 에이전트는 사람이 아니다.** `redteam` 을 쓴 작성자 8명과 라벨러 3명은 별도 컨텍스트의 LLM 이지만 설계자와 같은 모델 계열이다.
  라벨러 일치도가 완전한 것(판정·규칙 72/72, κ = 1)은 정책이 명확하다는 증거일 수도, 같은 계열이라 같은 방식으로 읽는다는 증거일 수도 있다. 이 저장소로는 구분하지 못한다.
- **`redteam` 에는 회색 지대 소재가 적다.** 작성자에게 '정책으로 분명히 판정되는 경우만 넣으라'고 요청했다. 가장 어려운 것(사람 심사자도 갈릴 법한 것)은 들어 있지 않다. `AD-ADV-01` 은 1건뿐이다([data/README.md](../data/README.md), [POLICY_GAPS.md](POLICY_GAPS.md)).
- **회색지대 셋(`gray`)은 이 약점을 일부만 푼다.** 작성자에게 갈릴 만한 소재를 일부러 넣으라고 했고(gray 60건), 라벨러 3명의 일치는 `clear`·`normal` 에서 100%, `gray` 에서 <!-- num:res.agreement_gray.slices.gray.mean_agreement_with_author|pct1 -->78.9%<!-- /num --> 였다([EVAL_GRAY.md](EVAL_GRAY.md) 7.3).
  그러나 작성자·라벨러가 모두 같은 모델 계열이라 '사람이 갈리는 곳'과 같다는 보장이 없다. 라벨러 표 360개가 전부 작성자 정답 또는 작성자가 적은 대안 판정이었다는 사실이 그 증거이자 한계다.
- **`redteam` 의 수정 후 수치는 holdout 이 아니다.** 첫 접촉 수치만 holdout 이다. 수정 뒤 수치는 실패 사례를 본 뒤 고친 결과다([F-10](FAILURES.md)).
- **`generated` 는 낙관적이다.** 생성기와 탐지기가 같은 어휘를 쓰므로 거의 만점이 나온다. 헤드라인으로 쓰지 않았다.
- **표본이 작다.** `test` 는 77건, `redteam` 은 72건이고, 정답이 REJECT/REVIEW 인 소재는 `test` 에서 27건·24건, `redteam` 에서 34건·17건이다. 한 건이 3~5%p 를 움직인다. 모든 비율에 분모와 Wilson 구간을 붙였다.

## 2. 탐지 능력

- **의미상 위반은 결정론 경로가 못 잡는다.** 레드팀 패러프레이즈 슬라이스에서 위험 승인율이 <!-- num:history.redteam_v1.redteam.full.slices.paraphrase.unsafe_approve|rpct1 -->87.5% (14/16)<!-- /num --> 다 ("손해 볼 일 없는 투자", "먹어 본 분 전원이 만족했어요").
  닫힌 어휘로는 열린 표현을 막을 수 없고, 막으려 어휘를 늘리면 평가셋에 맞춘 패치가 된다([D-11](DECISIONS.md)). 이를 위해 LLM judge 를 설계했고 실호출로 한 번 쟀다(3절): 같은 소재에서 <!-- num:judge_live.results.redteam.full+judge.slices.paraphrase.unsafe_approve|rpct1 -->0.0% (0/16)<!-- /num --> — 단, 한 번·한 모델·같은 모델 계열이다.
- **의미 범위가 필요한 정상 소재는 결정론이 반려한다.** 회색지대 첫 접촉에서 의원 서비스 광고의 '불면증 치료'(HLT 는 제품 효능), '한도 조회는 신용조회 없이'(조회 *단계*에 걸린 말), 이미지 글자의 '= 사기 신호' 라벨 3건이 남았다([F-22](FAILURES.md)).
  어휘 예외로 열면 구멍이 되고, judge 는 REVIEW 까지만 낼 수 있어([D-14](DECISIONS.md)) 이 반려를 되돌리지 못한다. 상호 속 '최고·최저' 예외는 상호를 광고주가 적는 값에 의존한다 — 상호에 낱말을 심어 우회할 수 있으나 순위·유일성 표현은 대상에서 뺐다.
- **어휘의 재현율은 불완전하다.** 질병명·시간 단위·동사 목록은 유한하다. 리뷰어가 찾은 변형은 넣었지만 다음 변형은 놓칠 수 있다. 정규화 표도 유한하다(한자 49자와 몇 종의 유사 문자만 접는다).
- **문형 공백은 문형이 다른 독립 셋에서만 보였다.** 이미지 셋은 정답 글자를 줘도 7/60 을 틀렸고 그 6건이 조사('앱을 설치')·동사('회신')·명사('감량')·경고 문형의 공백이었다([F-31](FAILURES.md)). dev · test · redteam 은 이 문형이 없어 조용했다.
  좁게 고친 뒤 그 셋의 정확도가 <!-- num:hist.vision_offline_after_fix.results.decision.oracle.accuracy|rpct1 -->98.3% (59/60)<!-- /num --> 가 됐지만 실패를 보고 고친 구성이라 *일반화의 증거가 아니다*. 새 독립 소재로 잰 적이 없다.
  알면서 남긴 것: 범위 설명 각주는 '최고' 가 문장 첫머리일 때만 풀려서 '새 학기 최고 할인율은 일부 모델에 한하며' 는 오반려되고, '원격제어 앱 설치 없이' 도 오반려되며, '보장' 없이 '체중' 이 낀 감량 주장('3주 만에 체중 8kg 감량')은 `fast_result` 가 못 본다.
- **tight 매칭은 낱말이 붙어 생기는 오탐을 구조적으로 안고 있다.** 우회("수 익 보 장")를 잡으려 공백을 지우면 "총 기능"이 `총기`로 읽힌다. 알려진 몇 개(`총기능`, `이유 일부`, `1 위치`, `오늘 만나는`)만 막았다([REVIEW.md M6](REVIEW.md)).
- **심사 엔진은 이미지를 이해하지 않는다.** `image_text`(이미지 속 글자)는 업스트림이 준 값이라고 가정한다 — 이 저장소의 `vision/` 이 VLM 으로 읽어 넣는 경로를 측정했다([EVAL_VISION.md](EVAL_VISION.md); 합성 이미지에서는 세 모델이 같았다). 이미지 자체의 위반(성적 이미지, 비교 이미지)과 정책에 없는 시각 단서(카운트다운 타이머, [POLICY_GAPS.md](POLICY_GAPS.md) 23번)는 다루지 않는다.
- **숫자 사이의 구분 기호 우회는 못 잡는다.** `1.0.0.%.만.족` 은 소수점과 구분할 수 없어서 걷어내지 않는다([FAILURES.md](FAILURES.md) F-4).
- **자모 하나 차이 정상어는 stoplist 로만 막는다.** `수익보상` 은 되지만 stoplist 밖의 근접어는 보류된다.
- **변형 표기는 REVIEW 까지만 간다.** 정책상 REJECT 인 철자 변형이 사람에게 넘어간다(안전 쪽 오차, [F-15](FAILURES.md)).
- **형태소 분석이 없다.** 조사·어미는 정규식으로 허용한다. 드문 활용형은 놓칠 수 있다.
- **심사 조작 시도(광고 문구 속 "승인으로 답하라")는 규칙이 아니다.** 다른 위반이 없으면 승인된다(결정론 경로는 문구를 데이터로만 다루므로 속지는 않지만, 의심해서 사람에게 보내지도 않는다). v2 후보다.
- **광고-랜딩 대조는 단위가 좁다.** 원·%·일/개월만 본다. 같은 단위의 서로 다른 개념(체험 7일 vs 환불 30일)은 구분하지 못해 '확인 불가'로 처리한다. 금액은 '3만 9천 원'·'천원'을 값으로 읽지만 "수만 원" 같은 어림은 대조하지 않는다.
- **수치는 소재의 *주장*과 랜딩 텍스트의 일치만 본다.** 랜딩 페이지의 진위·가격 인하의 사실 여부는 모른다. 랜딩 속 보장·질병 효능 표현은 사람 검토(REVIEW)까지만 낸다([D-13](DECISIONS.md)).
- **업종과 인증 여부는 검증할 수 없다.** `verified` 는 인증된 계정에서만 인정하지만, `category` 는 광고주가 적는다. 문구 단서(대출·금리·코인, 질병 효능)가 어긋날 때만 사람에게 보낸다. '주식·투자' 단독은 정상 광고에도 흔해 단서에서 뺐다.
- **이름만 든 비교("A사보다 저렴")는 배포 경로에서 탐지되지 않는다.** `ReviewConfig.competitors` 를 API·CLI 가 채우지 않는다(정책의 '타사·경쟁사' 표현만 본다).

## 3. LLM 경로

- **실호출은 한 번 쟀다**([JUDGE_LIVE.md](JUDGE_LIVE.md)): `claude-opus-5-5`, effort `medium`, 소재 209건에 한 번씩, GitHub Actions 에서. 요청(구조화 출력·`fallbacks: "default"`·시스템 블록 캐시)이 모두 받아들여졌고 실패·거절은 0건이었다.
  패러프레이즈 위험 승인율 <!-- num:judge_live.results.redteam.full.slices.paraphrase.unsafe_approve|rpct1 -->87.5% (14/16)<!-- /num --> → <!-- num:judge_live.results.redteam.full+judge_cap.slices.paraphrase.unsafe_approve|rpct1 -->0.0% (0/16)<!-- /num -->, 정답 APPROVE 소재 <!-- num:judge_live.pooled.approve_changed|rpct1 -->7.3% (5/68)<!-- /num --> 의 판정이 바뀌었고 그중 2건이 REJECT 였다 → 기본값을 상한 구성(Judge 는 REVIEW 까지만)으로 했다([D-14](DECISIONS.md)).
- **이 수치가 보여 주지 않는 것**: ① **소재당 한 번 호출**이라 같은 입력을 다시 넣었을 때의 변동을 모른다(경계 사례는 달라질 수 있다). ② 모델 하나·effort 하나·프롬프트 v1 이다 — 더 싼 모델, 다른 effort, 다른 프롬프트는 재지 않았다.
  ③ 소재·정답·라벨러·(대역)이 설계자와 **같은 모델 계열**이라 낙관 쪽 편향이 남는다. ④ 정답 APPROVE 는 68건이고 한 건이 1.5%p 다. ⑤ GitHub 러너에서 동시 4개로 3분 걸렸다 — 속도 제한, 긴 소재, 동시 요청이 많은 운영 환경은 재지 않았다.
- **서브에이전트 대역**으로 먼저 예측했고([JUDGE_REPLAY.md](JUDGE_REPLAY.md)) 핵심 결론(패러프레이즈 0/16, 상한 없이 정상 소재 REJECT 2건)은 실호출과 같았다. 달랐던 것은 양이다 — 실호출이 후보를 낸 소재가 <!-- num:judge_live.pooled.judge_added|kn -->54/209<!-- /num -->로 대역(<!-- num:judge.pooled.judge_added|kn -->28/209<!-- /num -->)의 약 두 배였고 규칙 단위 정밀도가 떨어졌다.
- **Judge 프롬프트·입력의 알려진 결함(고치지 않음)**: 규칙을 한 줄로만 요약해 정책의 예외를 모른다, 랜딩 텍스트가 입력에 없다(실호출 모델이 근거 문장에 그렇게 적었다), `already_found` 가 인용 없는 발견을 빼 같은 규칙을 지어낸 앵커로 다시 제안한다, 부재형 위반을 내는 방법이 정해져 있지 않다([JUDGE_REPLAY.md 4.4](JUDGE_REPLAY.md)). 고치면 다시 재야 한다.
- **인용 정확도**: 제안한 후보 <!-- num:judge_live.info.proposals|int -->76<!-- /num -->개 전부 원문과 일치했다(근거 없는 의심 0/209). 표본이 작아 '틀리지 않는다'는 증거는 아니다.
- LLM 은 위반을 **더할 수만** 있다. 결정론 경로의 오탐(정상 소재 오반려)을 LLM 이 바로잡지는 못한다.
- 예산 상한에 닿으면 프로세스가 끝날 때까지 모든 승인이 REVIEW 가 된다(기간 예산이 없다).
- **API 키는 GitHub 비밀값**으로만 쓰며 수동 워크플로(`judge-live`)가 읽는다. CI(`ci.yml`)는 API 를 부르지 않는다. 저장소가 공개라서 워크플로 권한은 최소로 나눴다(키가 있는 작업은 읽기뿐, 쓰기 작업에는 키가 없다).

## 4. 수정안

- 생성기는 템플릿이다. 문장이 거칠고 제목이 짧아지는 경우가 있다. '검증됨'은 재심사 통과 + 수치·단어 보존 + 문장 구조 검사(낱말 중간 절단, 괄호·따옴표 짝, 숫자 손실)를 뜻하며 **문장이 자연스럽다는 뜻이 아니다**('수준의 보습력 크림').
- 질병 표방·랜딩 불일치·제한 업종·사기성 유도·광고주 인증은 자동으로 고치지 않는다(광고주 입력이 필요하다).
- 이 절의 수정안은 '반려된 문구를 고쳐서 같은 심사에 다시 통과시키는' 고리다. 상품 페이지에서 처음부터 광고를 만드는 생성은 `creative/` 가 따로 한다([EVAL_CREATIVE.md](EVAL_CREATIVE.md)) — 사진을 생성하는 모델은 없고, 상품 일러스트에 문구·배지·버튼을 얹은 이미지 사양을 그린다.
- **수정안의 '검증됨'은 같은 엔진의 재심사에 기댄다.** 엔진이 놓친 다른 위반(뜻을 돌려 말한 표현)이 수정안에 남아 있어도 재심사는 통과한다. 수정안이 *정책에 맞는지*를 독립 라벨러로 잰 적은 아직 없다.

## 5. 운영

- **요청 하나가 서버를 멈출 수 있는 경로를 완전히 닫지는 못했다.** 정규식을 선형으로 만들고 증가율 테스트를 뒀지만, 요청 단위 CPU 예산이나 작업자 격리는 없다. 파이썬 `re` 가 GIL 을 놓지 않으므로 아직 모르는 비선형 입력이 하나 있으면 프로세스 전체가 선다. 속도 제한은 요청 수 기준이다([REVIEW.md C2](REVIEW.md)). 정규식 뒤의 후처리도 최대 크기 입력으로 재야 한다는 것을 CI 첫 실행이 보여 줬다([F-21](FAILURES.md)).
- **부하 수치는 이 기계의 것이다.** 동시 접속 1–128 에서 쟀지만 서버와 부하 생성기가 한 프로세스(GIL 공유)였고 루프백이었다 — 네트워크 지연, 여러 노드, DB 경합, 실제 트래픽 분포는 모른다. 동시 접속 32 이상에서는 SLO(p95 250ms)를 지키지 못했고, 한 광고주가 쏟아붓는 동안 다른 광고주의 *꼬리 지연*은 지키지 못했다([EVAL_OPS.md](EVAL_OPS.md) 9.4). 용량 계획으로 읽지 않는다.
- **단일 노드다.** SQLite 와 프로세스 안 레이트 리미터. 다중 인스턴스에는 저장소와 제한기를 교체해야 한다.
- **인증은 정적 베어러 토큰이다.** 만료·교체·범위가 없다. 감사 로그는 추가 전용이지만 변조를 막지는 않는다.
- **요청 크기 제한은 `Content-Length` 로만 건다.** 청크 전송은 거르지 못한다(필드 길이 제한은 있다).
- **Docker 이미지는 로컬에서 빌드하지 못했다**(이 개발 환경에는 데몬이 없다). GitHub Actions 의 `docker` 잡이 빌드·기동·헬스체크·요청 한 건·토큰 없는 시작 거부를 확인하고 통과한다. 비편집 설치로 정책 파일·콘솔 정적 파일이 패키지에 실리는지도 직접 확인했다.
- **GitHub Actions 는 저장소를 올린 뒤에야 처음 돌았다.** 첫 실행이 파이썬 3.11 에서 2차 시간 결함을 잡았고([F-21](FAILURES.md)) 고친 뒤 3.11–3.13·docker·e2e 가 모두 통과한다. 다만 절대 시간 예산(4초)은 공유 러너의 속도에 의존한다 — 더 느린 러너에서는 다시 흔들릴 수 있다.

## 6. 주장하지 않는 것

실제 광고에서의 정확도, 실제 심사자·광고주·운영자와의 일치도와 협업, 사람 심사 시간의 절감, 법적 적합성, 사진·손글씨 같은 실제 이미지의 이해, 실제 광고 계정의 성과 데이터에서의 이상 탐지, 생성물과 리포트가 *읽기 쉽고 쓸모 있는지*(사람 평가를 하지 않았다), 실제 트래픽과 다중 노드 운영.
모듈별로 잰 것과 못 잰 것은 각 `docs/EVAL_*.md` 의 '주장하지 않는 것' 절과 [FAILURES.md](FAILURES.md) 에 있다. 이 저장소의 어떤 수치도 production 에서 나온 것이 아니다.
